# 参考来源与借鉴边界

## 来源

[`cat-xierluo/legal-skills`](https://github.com/cat-xierluo/legal-skills) 下的：

- `skills/contract-copilot/references/review-framework.md` — 分层审查结构、四步流程、风险清单字段
- `skills/contract-copilot/references/revision-strategy.md` — 整改动作分类、最小必要修改原则、商务取舍边界

## 借鉴了什么

**1. 风险卡片的字段结构**

原框架用九个字段描述一个风险：名称｜等级｜后果｜判别标准｜推荐措辞｜示例｜法律依据｜整改建议｜相关条款。

本项目落到 `findings` 的字段是：`name` / `severity_label` / `category` / `rationale`（后果+理由）/ `evidence`（命中原文）/ `statutes`（法律依据）/ `suggestion`（整改建议）/ `remedy`（动作类型）。没有照搬"风险示例"和"相关条款"，因为本工具靠规则定位，示例字段没有承载物。

**2. 整改动作分类（`remedy`）**

原来每个风险点只是一段文字建议，现在明确归类为六种动作之一：局部删减 / 局部补入 / 局部替换 / 整条重写 / 批注提示 / 仅入意见书。

规则层按检查点性质推断默认动作（缺失型→补入，命中型→局部替换，低风险→批注），大模型可在 `local-replace` 等选项内覆盖。这直接来自 revision-strategy 的「动作选择顺序」。

**3. 最小必要修改原则**

「能局部改就不整条重写」。体现在 `default_remedy()` 的取值上——只有缺失型才用 `insert`，命中型默认 `local-replace` 而不是 `replace`。

**4. 商务取舍不代客户决定**

这是最有价值的一条。原文档明确：涉及价格、比例、期限、范围的改动属于商务取舍，未获授权时应批注提示而非直接拍板。

本项目把它落成了 prompt 的硬约束：模型生成建议条款时，涉及具体数值用 `【】` 占位（如「违约金按合同总额的【百分之X】计算」），并在分析里注明"需商务确认"。改动后实测，一份样例合同的 9 处条款文本都改成了占位形式。

**5. 签署前必检清单**

原框架有 7 项签署前检查。本项目在意见书里加了一节，能自动判定的（核心条款、验收闭环、违约解除、争议解决、通知送达、保密）按规则结果打 ✓ / ✗，无法自动判定的（主体资格、标的合法性）标 ○ 并注明需人工核验。

**6. 交付物结构**

原框架的「交付复核」要求输出风险清单、谈判顺序、签署前条件。本项目据此在意见书中新增「三、谈判顺序」和「四、签署前必检清单」两节。

## 没有借鉴的部分

| 内容 | 原因 |
|---|---|
| 宏观层（主体适格、标的合法、审批程序） | 需要核验营业执照、授权书、决议等外部材料，纯文本工具无法判断；本项目只标为"需人工核验" |
| P0/P1/P2 三级 | 与本项目的 high/medium/low 语义重叠但阈值不同，直接替换会让已有评测集失效；保留现有分级，通过 `remedy` 体现动作差异 |
| 12 类合同的专项审查文件 | 体量大（每类一个长文件），且多为人工判断项，不适合硬编码成规则；已用 31 个检查点覆盖其中高频的买卖/租赁/建设/服务 |
| DOCX 修订痕迹（track changes） | 技术要求高（需要 OOXML 层面的 run 级操作），不在本期范围 |
